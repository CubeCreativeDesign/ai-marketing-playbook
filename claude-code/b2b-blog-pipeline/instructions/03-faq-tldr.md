# Stage 3: Draft-Level QC, FAQ, and TL;DR Review

## Purpose
Stage 3 is the quality control checkpoint for the draft produced by Stage 2. It runs in two phases:

1. **Draft-Level Quality Control** — Run your QC script (`scripts/qc.sh`) against the draft, if configured. React to the auto-generated QC report block by fixing every flagged item, then re-run to confirm a PASS. Perform the manual semantic checks (standalone readability, H2 answer-pattern) that the script cannot automate.
2. **FAQ and TL;DR Review** — Review the FAQ and TL;DR sections for accuracy, completeness, consistency, and voice. This is a refinement pass, not a rebuild.

Run Phase 1 first, end-to-end, before starting Phase 2. The script is deterministic — running it produces evidence that the checks actually happened.

**Output feeds:** Stage 4 reads this draft to write the titles, meta description and keywords, and counts its list items for any number in a title, so the body, TL;DR and FAQ must be final here. The TL;DR and FAQ ship as written inside their template tags. Stage 9 re-runs scripts/qc.sh on this file.

**Human check:** None inside the pipeline: this stage runs unattended under `claude -p`. Drafts stay in `output/`, with no Drive upload, and an editor reads the finished draft there before it publishes. The items the editor must see are the attributed-quote hits Step 4 flags for human review: list them first in your Stage 3 notes.

---

## What Stage 3 Does NOT Do
- Does not rewrite the main blog content beyond fixing prohibited phrases and structural violations
- Does not change the structural format established by Stage 2 (TL;DR wrapper, FAQ wrapper, # Links heading)
- Does not generate FAQ or TL;DR from scratch
- Does not add links to the TL;DR section (no links in TL;DR, ever)
- Does not handle internal or external link verification — those are Stages 6, 7, 8

# Phase 1: Draft-Level Quality Control

## Step 1: Run Your QC Script Against the Draft

If you have a QC script set up, run it from the project root:

```bash
bash scripts/qc.sh output/[topic-slug]-draft.md --append
```

The `--append` flag writes the QC report directly into the draft as a `## Stage 3 QC Report (auto-generated by qc.sh)` block at the bottom of the file. The block is internal-only and will be stripped by the CMS publishing step.

The script runs three checks:
- **Prohibited-phrase scan** against every term in `reference/prohibited-phrases.md`, classifying each hit as `agency_voice` (must fix), `in_blockquote` (preserve verbatim), or `in_attributed_quote` (preserve verbatim, flagged for human review)
- **Readability metrics** on the main body only (TL;DR, FAQ, and Links section are stripped before measurement): Flesch-Kincaid grade, Flesch Reading Ease, em-dash density, average sentence length, passive voice ratio
- **Structure check** for bold-as-heading violations, horizontal rules in body, and H4+ headings

The script auto-discovers `reference/prohibited-phrases.md` by walking up from the draft's location. If the script errors out with a "could not find reference file" message, pass it explicitly:

```bash
bash scripts/qc.sh output/[topic-slug]-draft.md --reference reference/prohibited-phrases.md
```

## Step 2: Read the Generated Report Block

Open the draft. The QC report block sits at the bottom. It has four subsections:

1. **Prohibited-Phrase Scan** — A summary with hit counts plus a table of every hit with line number, section, and classification
2. **Readability Metrics** — Word count, Flesch-Kincaid grade, Flesch Reading Ease, em-dash count, passive voice ratio, with PASS/WARN/FAIL status per metric
3. **Structure Check** — Counts and a table of violations with suggested fixes
4. **Overall QC Status** — PASS, WARN, or FAIL with required actions

Do not skim the report. Each item gets a defined response in the following steps.

## Step 3: Fix Every Prohibited-Phrase Hit Classified as Agency Voice

For each row in the Prohibited-Phrase Scan table labeled **FIX agency voice**:

- Navigate to the line number listed
- Identify the prohibited term in context
- Rewrite the sentence using a natural alternative — do not just delete the word. Restructure so the replacement reads as if it were always there.
- Test the rewrite against the reading-level target (Flesch-Kincaid grade 9 or lower) and the persona voice

Common replacements:
- "leverage" → use, apply, draw on, take advantage of
- "streamline" → simplify, tighten, speed up, clean up
- "dive into" → look at, cover, get into, walk through
- "in today's [landscape/world/market]" → today, currently, right now, (or just delete and start the sentence directly)
- "robust" → strong, solid, well-built, thorough
- "unlock" → reach, find, get to
- "delve" → look at, explore, examine
- "navigate" → handle, work through, get through
- "holistic" → complete, full-picture, end-to-end
- "cutting-edge" → current, modern, recent (or describe the specific feature)
- "utilize" → use
- "foster" → build, grow, encourage
- "harness" → use, put to work

These are starting points. Pick the replacement that actually fits the sentence — not the closest synonym.

## Step 4: Handle Blockquote and Attributed-Quote Hits

For each row labeled **Keep (blockquote)** or **Review (attributed quote)**:

- The script preserved the term verbatim because it sits inside a direct quote
- Leave the quote text as-is — verbatim quotes must remain verbatim, even when they contain banned terms
- For **Review (attributed quote)** rows specifically: flag the quote in your Stage 3 notes for human review. The reviewer may decide to swap the source or paraphrase rather than quote verbatim. That decision is not yours to make at this stage.
- Do not "fix" prohibited terms inside quotes. Doing so misrepresents the source.

## Step 5: Apply Suggested Fixes from the Structure Check Table

For each row in the Structure Check table:

- **Bold-as-heading violations:** Replace `**Text.**` followed by a paragraph with `### Text` (a proper H3 heading). The suggested fix is provided in the table — apply it exactly.
- **Horizontal rule violations:** Remove the `---` / `***` / `___` line and replace with a proper heading if the line was being used as a section divider. [YOUR_AGENCY] uses heading hierarchy, not horizontal rules, for visual separation.
- **H4+ heading violations:** Promote H4 (`####`) to H3 (`###`), or restructure the section to fit under existing H2/H3 hierarchy. [YOUR_AGENCY] content uses H1-H3 only.

## Step 6: Address Readability Failures

Look at the Readability Metrics subsection. For each metric labeled **FAIL** (not WARN):

- **Flesch-Kincaid grade above target (above 10):** Simplify. Break long sentences. Replace multi-syllable jargon with common words. Sample a few paragraphs and rewrite the densest ones.
- **Em-dash ratio above 1 per 300 words:** The readability row labels this FAIL, but it never escalates the overall status to FAIL on its own — em-dash overuse produces at most an overall WARN. Fix it anyway. Search the draft for em dashes (—) and replace the excess with semicolons, periods, or parentheses. Pick the punctuation that fits the sentence, not the closest one-to-one swap.
- **Avg sentence length above 22 words:** Find the longest sentences. Split them into two or three shorter sentences. Active voice helps here.
- **Passive voice ratio above 15%:** Find sentences using "was/were/been" + past participle. Flip them to active voice ("the team launched the campaign" instead of "the campaign was launched by the team").

WARN status (below target rather than above) is acceptable and does not require action. Easier-to-read prose is fine for the operator audience. Only act on FAIL items — with one exception: if the only thing pushing the overall status to WARN is em-dash density, treat that as a fix-it per the em-dash note above.

## Step 7: Perform Manual Semantic Checks the Script Cannot Do

The script catches detection. Two checks require semantic judgment and must be done manually:

### 7a. Standalone Readability Check

For each H2 and H3 section in the main body, ask: if a reader pulled this section out of context — or an AI search engine cited only this block — would it still make sense?

Look for sections that start with:
- "This approach..."
- "As mentioned above..."
- "The next step is..."
- "Building on that..."
- "However, this only works if..."

These signal a dependency on prior context. Fix by adding a brief framing sentence at the start that names the topic so the block stands alone.

This matters for both human skimmers and AI search engines that chunk content for citation at the heading-and-answer level. A block that can't stand alone is less likely to be cited and harder to scan.

### 7b. H2 Question + Answer Pattern Check

For each question-format H2, confirm all four of the following:

1. The answer follows immediately after the heading — no intervening images, lists, or other content
2. The answer is approximately 50 words (±20%, so 40-60 words)
3. The first sentence directly answers the question — definition, recommendation, or yes/no — not backstory
4. The following sentences provide detail, reasoning, or example

If a section opens with context before answering, restructure so the answer leads. If the answer is too long or too short, tighten or expand it to the 40-60 word window.

## Step 8: Re-Run Your QC Script to Confirm

After making all fixes, re-run:

```bash
bash scripts/qc.sh output/[topic-slug]-draft.md --append
```

The script is idempotent — the previous report block is stripped and replaced with a fresh one. Verify:

- Overall QC Status is **PASS** or **WARN** (not FAIL)
- All agency_voice prohibited-phrase hits are now zero (any remaining hits should only be in blockquotes or attributed quotes)
- Structural violations are zero
- Readability metrics either PASS or WARN

If the report still shows FAIL, the fixes were incomplete. Address remaining items and re-run.

Once the report shows PASS or WARN with no required fixes outstanding, Phase 1 is complete. Proceed to Phase 2.

# Phase 2: FAQ and TL;DR Review

This phase refines the FAQ and TL;DR sections. Phase 1 already cleaned up prohibited phrases, structure, and readability at the draft level — including the FAQ and TL;DR. Phase 2 focuses on content quality of those two sections specifically.

## TL;DR Review

### Review Criteria
Read the full blog post, then evaluate the existing TL;DR against these standards:

1. **Accuracy** — Does every bullet correctly represent what the main content actually says? Flag and fix anything that overstates, understates, or misrepresents a point.
2. **Completeness** — Are all major takeaways captured? If the post has a key insight that a busy [YOUR_VERTICAL] owner would need to know, it must be in the TL;DR.
3. **Consistency** — Do the statistics and claims in the TL;DR match the main content exactly? No rounding, no paraphrasing numbers differently.
4. **Conciseness** — Each bullet should be 1-2 sentences. Cut anything that restates what another bullet already covers.
5. **Value** — Would a [YOUR_VERTICAL] owner who ONLY reads the TL;DR walk away with the right takeaways? If not, fix it.
6. **Voice** — Does it match the writer persona used in the post?
7. **Introduction Heading** — Does the `## Introduction:` heading contain a short, SEO-focused title (under 80 characters)? Does it include the primary keyword? Is it inside the wrapper (before `{{endTLDR}}`) with the intro paragraph outside?

### TL;DR Rules
- 3-5 bullet points maximum
- Each bullet: 1-2 sentences
- Include the most compelling statistic from the post
- End with the action item or CTA
- **NO links in the TL;DR — none, ever**
- Bold key numbers and critical terms within bullets

### TL;DR Template Tag Format
The TL;DR section MUST be wrapped in CMS template tags exactly as shown. The introduction paragraph follows the TL;DR inside the wrapper — this keeps both the TL;DR and intro from showing in the blog feed.

```
### TL;DR
{{TLDR}}

[TL;DR bullet points here]

## Introduction: [Short SEO Title, Under 80 Characters]
{{endTLDR}}

[Introduction paragraph starts here — outside the wrapper]
```

Do NOT deviate from this format. The `{{TLDR}}` and `{{endTLDR}}` tags are required for the CMS automation. The introduction heading sits inside the wrapper. The introduction paragraph sits outside.

### Improvement Actions
- Replace weak bullets with stronger takeaways from the main content
- Tighten language — remove filler words and vague phrasing
- Ensure the most important point comes first
- Verify every number matches its citation in the main content

## FAQ Review

### Review Criteria
Read the full blog post, then evaluate each FAQ question and answer:

1. **Relevance** — Are these the questions a [YOUR_VERTICAL] business owner would actually ask after reading this post? Replace any weak questions with stronger ones based on:
   - What would someone Google after reading this?
   - What objections might make a business owner hesitate?
   - How do they actually implement this with their team and budget?
   - What's the investment and expected return?
   - How does this compare to what their competitors are doing?

2. **Accuracy** — Does every answer correctly reflect the main content? No contradictions, no invented claims, no statistics that don't appear in the post.

3. **Completeness** — Does each answer fully address the question? A [YOUR_VERTICAL] owner reading just the FAQ should get a useful, actionable response.

4. **Consistency** — Do the answers align with the tone, data, and recommendations in the main post? If the post recommends X but the FAQ implies Y, fix it.

5. **Voice** — Do the answers match the writer persona? If the post uses an approachable, analogy-driven voice, the FAQ shouldn't suddenly sound clinical.

6. **Scannability** — Can a busy reader quickly find the key information in each answer? Answers should use:
   - Bold emphasis on key numbers, benchmarks, and critical takeaways
   - Short paragraphs (2-4 sentences max)
   - Bullet points or numbered lists where appropriate within answers
   - Clear opening statement that directly answers the question

### FAQ Rules
- 3-5 questions (match what Stage 2 produced unless a question is clearly weak)
- Questions phrased the way a [YOUR_VERTICAL] business owner would actually ask them
- Question headings (H3) use AP title case, same as every other heading — see the Capitalization section of `reference/mechanical-style-rules.md` (single source of truth)
- Answers: 2-4 sentences for simple questions, structured with subheadings/bullets for complex ones
- At least one question should naturally link to a [YOUR_AGENCY] service page or another blog topic
- Format for FAQ schema markup compatibility (JSON-LD)

### FAQ Template Tag Format
The FAQ section MUST be wrapped in CMS template tags and use H3 headers for questions with answers directly below. No extra formatting between question and answer.

```
## Frequently Asked Questions
{{FAQ}}

### This Is the First FAQ Question?
This is the direct answer to the question. Keep it concise and actionable.

### This Is the Second FAQ Question?
And this is the answer to that question. No blank lines or extra formatting between the H3 and the answer text.

{{endFAQ}}
```

Do NOT deviate from this format. The `{{FAQ}}` and `{{endFAQ}}` tags are required for the CMS automation.

### Improvement Actions
- Replace any question that no real [YOUR_VERTICAL] business owner would ask
- Strengthen weak answers with specific data from the main post
- Add a linking opportunity if none exists (one question should point toward a service page or related content)
- Ensure no two questions cover essentially the same ground
- Tighten answer language — cut fluff, get to the point

## Phase 2 Re-Run of Your QC Script

If you made content edits to the TL;DR or FAQ during Phase 2 (replacing a bullet, rewriting an answer), re-run `scripts/qc.sh --append` to confirm no new prohibited phrases or structural issues were introduced. The script is fast — there is no reason not to verify.

---

## Process Summary

1. **Phase 1: Draft-Level QC**
   - Step 1: Run `bash scripts/qc.sh <draft> --append` from project root (if configured)
   - Step 2: Read the QC report block appended to the draft
   - Step 3: Fix every agency voice prohibited-phrase hit
   - Step 4: Handle blockquote and attributed-quote hits (leave verbatim; flag for human review)
   - Step 5: Apply suggested fixes from the structure check table
   - Step 6: Address readability FAIL items (em-dash density, grade above 10, sentence length, passive voice)
   - Step 7: Manual semantic checks (standalone readability, H2 answer-pattern)
   - Step 8: Re-run scripts/qc.sh to confirm PASS
2. **Phase 2: FAQ and TL;DR Review**
   - Review TL;DR against criteria above
   - Review FAQ against criteria above
   - Make changes directly in the draft
   - Re-run scripts/qc.sh if you edited content

## Output
Save the updated draft to `output/[topic-slug]-draft.md` (overwrite the Stage 2 file).

The draft at this point should contain:
- The Stage 2 draft content (now QC'd and refined)
- The auto-generated Stage 3 QC Report block at the bottom showing PASS or WARN

Later stages (4-8) will add their own content above the QC report. The report block stays in place through Stage 8 for traceability and is stripped by the CMS publishing step before the post goes live.
